# A later matched evaluation

Use this only when a comparative evaluation is explicitly authorized. Updating
instructions, writing a protocol or verifying a fix does not start a generation
batch or preference test. The current repository's next comparison remains on
hold under [#26](https://github.com/drevendev/Silicon-Design/issues/26) and
[#23](https://github.com/drevendev/Silicon-Design/issues/23); a future run needs
separate authorization. This document is a protocol contract, not a run receipt.

## Match the work that the claim requires

Before a later launch, record the critical fixes and their scoped verification.
Pin the current product revision, exact instruction packages and supplied
materials. Preserve earlier originals, attempts and results; assisted corrections
or newer input belong to a separate record.

For a claim about a product, give every method the same complete requested screen
set and implementation permissions. Each method establishes or reuses its own
[shared kit](product-contract.md) before screen expansion; keep methods isolated.
Include kit creation, loaded context, tools and all attempts in the same total
time/cost allowance. Match model settings and report unavailable billing rather
than treating shorter instructions as measured cost parity.

Allow the structural work being assessed: authorized DOM/copy/control
simplification while preserving capabilities, exact data and product rules.
A fixed-DOM/CSS-only task tests presentation under that restriction. It cannot
establish ability to replace controls or remove fixed copy. Isolated screens
without a shared contract cannot establish shared implementation quality.

Carry accepted changes, explicit arrangements/capacity and supplied growth
constraints. Do not invent features to manufacture a difficult test.

## Predeclare handling before generation

Record pairing, side/order rules, attempts, stopping, permitted repairs, failures,
technical exclusions and available telemetry. Include whole-product consistency
and scoped screen decisions. Define a readability/function gate separately from
preference: inspect real text/glyph pairs and crops, relevant shared states and
actual input where available. Packaging and raster checks are not design review.

Retain failed/absent/invalid outputs. Do not selectively rerun or polish a method
until it wins. If a technical repair is allowed, retain the original, cause,
changed bytes and affected scope. A perceived colour mismatch or disliked but
usable design is not automatically a technical exclusion. An unresolved genuine
readability defect stays a failed/unresolved finding even if another swatch pair
passes. If the environment cannot verify a required path, report the limit.

## Analyse only the evidence obtained

Keep raw winner/tie/comments and technical flags. Read criticism of winners:
relative preference is not final acceptance. Record participant count and actual
method/opponent exposure. Missing answers after an early stop are not ties,
losses or a completed tournament; unequal exposure limits overall ranking.

Separate source assertions, rendered/native checks, preference and billing.
Do not pool unlike experiments or replace another environment's exact acceptance
with a substitute fixture. A future result may support a scoped conclusion;
this guidance change alone supports no quality, cost or audience claim.
