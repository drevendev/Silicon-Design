# Composition, spacing and density

Give space a job: establish relationships, reading order, comparison or focus. Start from content structure before selecting a grid.

## Compose the decision

Write the content in priority order without cards or columns. Group things that answer the same question. Place explanations near the action or value they explain. Use alignment to make comparisons effortless and proximity to show relationships. A shared border is useful when it marks a genuinely independent object; it need not wrap every paragraph.

Choose a dominant area appropriate to the surface: a representative result on a site, an unresolved work queue in an app, the playfield and immediate resource decision in a game. Different parts of a page may have different rhythms, while sharing alignment and a spacing vocabulary.

## Establish a spacing vocabulary

A 4 CSS px base with steps such as 4, 8, 12, 16, 24, 32 and 48 can be a convenient web starting point. Use smaller spaces within related groups and larger spaces between groups. Type metrics and optical alignment may need exceptions. Do not quantize everything merely because the grid exists.

Density follows task and input. A data tool may need compact rows to enable scanning; a reading site benefits from longer pauses. Compact visuals can retain generous hit areas. Avoid enlarging every app control until the primary work disappears below the fold.

## Let the layout adapt

Use content pressure to choose breakpoints. Decide which regions wrap, stack, collapse or scroll and retain a logical DOM reading order. Test intermediate widths and landscape, not only named phone and desktop sizes. Essential controls and explanations should not become hover-only on touch.

At narrow widths, a table can keep intentional horizontal scrolling when its two-dimensional relationships are necessary. Give that region a label and a discoverable scroll affordance. Do not force every table into cards if doing so destroys comparison. For ordinary prose and controls, avoid page-wide horizontal overflow.

## Check difficult content

Use zero, one and many items; a multi-line title; unbroken identifiers; localized dates; negative and large values; missing imagery; and translated actions. Prefer resilient wrapping and bounded media over arbitrary fixed heights. Test errors where they actually appear, not in a separate perfect mockup.

On canvas and game HUDs, specify safe areas, UI scale and draw order relative to the playfield. Those constraints require runtime inspection beyond web breakpoint checks.
