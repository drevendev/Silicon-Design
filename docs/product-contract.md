# One product across requested screens

Use this procedure for multi-screen work or a reusable component change. Reuse
the existing system first. A local correction does not require a new kit,
framework, canvas, component sheet or documentation bundle.

## Establish the working source

Name the current revision and requested surfaces. Carry accepted changes, real
content/values, explicit arrangement and capacity limits, and supplied growth
plans. Separate current requirements, authorized future work and speculation.
Resolve consequential ambiguity; do not invent content or silently substitute a
historical capture for the current product. Keep fixed-copy, CSS-only or other
implementation restrictions explicit. Report the redesign they prevent.

## Make the smallest shared kit

Use the product's token/source format and DESIGN.md where present. Keep one
authority for the changed roles and components:

| Contract | Decisions to share |
| --- | --- |
| Palette | Surface, text, icon, boundary, focus, action and status mappings; theme/state variants |
| Type and density | Reading/UI/numeric hierarchy, row widths, spacing, quantities and units |
| Common chrome | Navigation, headers, level/progress, selection and shared help |
| Repeated objects/actions | Content limits, grouping, semantics, input, states and recovery |
| Growth and response | Long translations, large/live values, supplied capacity, wrapping and scroll rules |

Extend an existing palette coherently or remap it within the authorized direction.
An isolated new hue is not a system; preserving every old hue is not a duty.
Keep icon meaning, edge/stroke/material relationships and semantic status cues.

Reuse implementations, not manually copied values. When work uses separate
contexts, pass the same compact contract, relevant components and revision to
each consumer. Do not pass every skill, research history or the whole project.
Changed shared components propagate to all requested consumers. A task-based
exception is useful; accidental screen-specific reinvention is not.

## Expand from a checked component

Inspect a representative populated use-size component before repeating it.
Check actual text/glyph surfaces and bounds, not just palette swatches. Exercise
affected controls and states when runtime is available; otherwise mark them
unverified. Remove redundant presentation or recompose the task when authorized,
preserving data, actions and accessible meaning.

Check equivalent components across the requested screens, relevant widths and
languages. Keep quantities, costs and actions together without hiding necessary
text or reducing hit areas. Deliberate reflow and content-driven height remain
valid. Recheck affected consumers after a common fix.

Deliver the shared changes, meaningful exceptions, actual checks and remaining
limits. A plausible kit or passing source check does not prove rendered quality.
Use the [workflow](workflow.md); comparisons have a [separate gate](evaluation.md).
